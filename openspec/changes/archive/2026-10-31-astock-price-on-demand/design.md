## Context

动机与实测事实见 `proposal.md`。设计前先钉住三条读自本仓的约束：

- **`read_range` 已经是"读缓存→缺失/过期才抓→回写"**（`fetch/dispatch.py:_read_range_one`）。方案 A 不需要新机制。
- **`cache.is_stale` 对已完结周期返回 False**（`_period_final`）。所以一次窗口读完之后，历史点永不再抓，只有当天那一格受 `daily` 的 20h TTL 管。这正是"按需 + 留存"要的语义。
- **`read_range` 的已知缺陷写在它自己的 docstring 里**：部分覆盖按 staleness 判定，fresh-but-incomplete 的缓存会原样返回、不补不报。对价格序列这是**静默错数据**。
- **`observation-reading` spec 明确要求 `read_series` 不联网**（"gaps are gaps, not surprise fetches"）。方案 A 要联网，两者必须显式分开而不是把读变成隐式抓。
- **没有交易日历**（`grep trade_cal|is_trading_day` 零命中）。覆盖度判定不能依赖"应该有几天"这种需要日历的算法。

## Goals / Non-Goals

**Goals:**
- 一个 (标的, 区间) 的价格请求，返回**要么完整、要么明确标注缺哪段**，绝不再静默返回不完整序列。
- 缺的段补抓，**已覆盖的段不重抓**（补数成本与缺口大小成正比，不与窗口大小成正比）。
- "读"（不联网，快，可复跑）与"补"（联网，慢，一次性）是两种显式意图。
- 活跃池预热让常用标的首次请求就是毫秒级，且预热失败不影响请求路径。
- 回测能钉住"当时那份数据"（序列指纹）。

**Non-Goals:**
- 不做全市场预灌（用户已裁决）。
- 不做实时行情、分钟级、tick 级。
- 不做复权口径回填/迁移（前复权序列被上游重写是既有事实，本变更不试图冻结它）。
- 不引入交易日历（见 D1）。
- 不改 `PaperExecutionService`、不改回测引擎、不改 `fd-quant`。

## Decisions

### D1. 覆盖度判定用"边界 + 内部空洞"，不用交易日历

**选择**：一个窗口 `[start, end]` 对某标的"已覆盖"当且仅当：①缓存里存在日期 ≤ start 的最近一点 或 该标的最早缓存日期 ≤ start；②存在日期 ≥ end 的最近一点 或 该标的最晚缓存日期 ≥ end；③窗口内已缓存点数 / 该标的在窗口内的**实际交易日数**（用"该标的全历史已缓存日期"去重集合交窗口来估）不低于阈值。

**理由**：没有交易日历，任何"应该有 250 个交易日"的算法都会在停牌、节假日、上市前区间上错判。**改用数据自身推断**：同一标的的已缓存日期集合就是它自己的交易日历（价格只在交易日有值）。这带来一个诚实的限制：**冷标的（零缓存）无法判定覆盖度**，此时唯一正确的行为是"整段抓一次"，而这恰好也是冷启动该做的事。

**备选**：引入 akshare `tool_trade_date_hist_sina` 做真日历。否——多一个会变的依赖，且停牌标的仍然不在日历里。

**这条决定的可测后果**：一个"边界够、中间有洞"的窗口会被判为未覆盖并补洞；一个"边界不够"的窗口会补边界段。两者都不重抓已覆盖部分。

### D2. 补数补"缺失段"，不重抓整段

**选择**：覆盖度判定输出**缺失区间列表**（可能多段），对每段发一次上游范围请求（`_build_range_params` 已支持 start/end），落库后重新读取。

**理由**：重抓整段会让成本与窗口大小成正比（730 天窗口哪怕只缺 3 天也要重抓 730 天），且会把已冻结的历史点用新抓的值覆盖——**前复权序列会被上游整体重写**，这等于用今天的口径改掉昨天的历史，破坏可复跑性。

**关键实现约束（已核实）**：`write_cache_range`（`fetch/cache.py:424`）是**批量 upsert**——对已存在行会 `obs.value = str(value)` 覆盖。补数若走它，"补洞"就变成"用今天抓到的前复权值改写已冻结的历史"，破坏可复跑性（同一 run 昨天算得出、今天算不出）。故补数路径**必须**用只插不改的变体（`ON CONFLICT DO NOTHING` 语义，与 `migrate.py:migrate_astock_daily` 同款），本变更新增该变体而不改 `write_cache_range` 本身（首次抓取仍需 upsert 以刷新当日格）。

**备选**：重抓整段并覆盖（简单，但破坏复跑性与历史稳定性）。否。

### D3. `fill_gaps` 是显式参数，默认 false

**选择**：`read_series` 增加 `fill_gaps: bool = false`。默认行为与今天完全一致（不联网，缺口就是缺口）。`fill_gaps=true` 时才走 D1/D2 的补数路径。**新增一个独立工具 `read_series_filled`** 而非只加参数？

**决定：只加参数，不加新工具。** 理由：工具面的膨胀是有代价的（每个工具都是一份需要维护的 schema 与文档），而 `fill_gaps` 是一个布尔开关，语义在同一工具内是清晰的；新工具会让"我该调哪个"变成调用方的负担。`read_series` 的 spec 要求"不联网"改为"**默认不联网**"，并新增一个 scenario 钉住 `fill_gaps=true` 时才联网。

**备选**：新工具 `read_series_filled`（工具面 +1，语义更"纯"但多一处要同步）。否。

### D4. 序列指纹 = 内容哈希，不落库

**选择**：对 `(entity_id, start, end, 排序后的 (date, value) 对)` 做 sha256，返回在读取结果里。run 记录把指纹存进自己的字段（fpt 侧已在 `strategy_runs.params` 有位置），**DAAS 侧不新增表**。

**理由**：指纹是"这次读到的东西"的属性，不是数据本身的属性——同一段数据被两个不同窗口请求会得到不同指纹，落库反而要处理"谁的指纹算数"。由调用方记录，语义最清楚。

**可测后果**：同一窗口连读两次，指纹相同（证明读取确定）；补数后再读，指纹变化（证明数据确实变了）——这两个断言一起把"可复跑"钉住。

### D5. 活跃池 = 显式配置 ∪ 近期请求频次

**选择**：池成员来自两处：①配置（`prices.pool` 表或配置项，显式自选）；②近期请求统计（按 (entity_id, 窗口) 的请求计数，取 Top-N）。预热 = 对每个成员按其配置深度（默认 730 天，与回测上限一致）走 D2 的补数路径。

**理由**：纯显式池要人维护，纯频次池冷启动为空。并集让"我知道重要的"与"实际被用的"都进来，且频次部分会随时间自动收敛到真实使用。

**预热的边界**：预热是**离线动作**（CLI/定时），**不在请求路径上**。预热失败只记录，不影响任何读取——一个标的抓不到不能让整池预热失败，更不能让请求失败。

### D6. 补数失败 → 返回已覆盖部分 + 明确缺口标注，绝不静默

**选择**：补数尝试全部失败时，返回已覆盖的点，并带 `gaps: [{start, end}]` 与 `fill_attempted: true, fill_failed: true`。**不抛异常**（部分数据比没有数据有用），但**必须标注**。

**理由**：这正是当前缺陷的反面——今天不完整序列被当成完整序列返回。标注让调用方（回测）能决定"用这 12 天算还是拒绝"，而不是被蒙。

**与回测的契约**：fpt 侧的回测应当**在 `gaps` 非空时拒绝运行**（或至少把缺口写进 run 记录），否则"按 12 天算出一个收益率"会看起来像真结果。这一条属于 fpt 的消费侧纪律，本变更只保证 DAAS 侧如实标注。

## Risks / Trade-offs

- **[覆盖度用数据自身推断 → 冷标的判不出覆盖]** → 冷标的直接整段抓一次，这正是它该做的；判不出的情形退化为"保守地补"，不会漏。
- **[补数不覆盖 → 上游修订的旧值永远不更新]** → 这是**刻意的**：历史点一旦落库就是冻结事实，改它会让旧 run 不可复跑。若确需刷新，走显式的"重建某标的某段"动作（本变更不含，记为后续）。
- **[前复权序列的口径漂移]** → 不解决，但**暴露**：同一 (标的, 区间) 在不同时间抓到的 qfq 值不同，指纹会变。run 记录钉住指纹即可事后发现"这两次不可比"。
- **[活跃池频次统计的存储]** → 只需 (entity_id, count, last_requested_at) 三列，量级是标的数（几千），可忽略。
- **[`fill_gaps=true` 的延迟]** → 补数可能要 0.3–1s/段，多段更久。这是显式请求补数的代价，调用方知情；默认路径不变慢。
- **[与 `write_cache_range` 的 upsert 语义冲突]** → **已核实为真**：它覆盖已存在行（`fetch/cache.py:424-458`）。故补数必须用只插不改的变体，否则补洞会改写历史（D2 已写明，tasks 里单列一项验证"补数不覆盖已有值"）。

## Migration Plan

1. 覆盖度判定 + 缺口计算（纯函数，可离线测）。
2. 补数路径（只插不改）+ 降级标注。
3. `read_series` 的 `fill_gaps` 参数（默认 false，先保证默认路径零变化）。
4. 序列指纹。
5. 活跃池（表/配置 + 频次统计 + 预热 CLI）。
6. 回滚：`fill_gaps` 默认 false，删掉参数即回到今天的行为；活跃池是独立动作，不参与读取路径。

## Open Questions

- 活跃池的 Top-N 取多少、频次窗口多长（实施时按真实请求分布定，spec 只要求"可配置"）。
- 预热的历史深度默认 730 天（对齐 `max_backtest_days`），是否需要更长（估值套件要算 5 年 CAGR？）——实施时看估值套件的实际窗口需求，spec 只要求"按配置"。
- 是否需要一个显式的"重建某标的某段"动作（覆盖已冻结历史）——本变更不做，记为后续；若上游勘误频发则值得单独立项。
